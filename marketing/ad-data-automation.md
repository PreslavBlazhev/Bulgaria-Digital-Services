## Решението: Google Ads Scripts, не Google Ads API

Архитектурата по-долу описваше API слой с OAuth. За един рекламен акаунт това
е излишна сграда.

| | Google Ads API | **Google Ads Scripts** |
|---|---|---|
| Developer token | иска се, одобрява се от Google | не |
| OAuth клиент + refresh token | иска се | не |
| Къде живее тайната | някъде, което трябва да пазим | няма тайна |
| Сървър | нужен | не — Google го изпълнява |
| График | пишеш го сам | вграден, в същия екран |
| Достъп до Sheets | през API | `SpreadsheetApp`, вградено |
| Много акаунти наведнъж | да | не |
| Писане назад в кампаниите | да | ограничено |

BDS има един акаунт и чете. Затова: **Scripts**.

Кодът е `tools/ads/google-ads-script.js` — слага се в
**Google Ads → Tools → Bulk actions → Scripts**, попълва се `SPREADSHEET_URL`
и се пуска на дневен график.

API-то остава правилният избор, ако акаунтите станат много или трябва да се
пише назад в кампаниите. Дотогава по-простото решение е и по-надеждното.

### Meta

За Meta няма такава среда — данните идват през Marketing API с HTTPS заявка.
Кодът е `tools/ads/MetaImport.gs`, в същия Apps Script проект като CRM-а.
Токенът живее в **Script Properties**, не в код и не в таблица.

Функциите отказват работа с ясно съобщение, докато няма акаунт — вместо да се
преструват на успешни.

### Тестове

`node tools/test-ads-import.mjs` пуска двете реализации на UPSERT-а — тази в
`Logic.gs` и тази в скрипта за Google Ads — върху един и същ вход и изисква
еднакъв изход. Две копия се разминават, освен ако нещо не ги сравнява.

## Защо изобщо

При 10 €/ден и една кампания ръчното пренасяне отнема пет минути дневно и е
поносимо. Проблемът идва при мащабиране: три кампании по два канала са шест
реда дневно, и някой ден се пропускат. Ръчните данни имат навика да имат дупки
точно в дните, които после ще искаш да анализираш.

**Правилният момент да се направи:** преди мащабиране, не след него.

## Разделянето е правило, не подредба

## API слоят пише **само** сурови метрики.

Никакви изчисления, никакви поправки, никакво „това число изглежда странно“.
`Spend`, `Impressions`, `Clicks`, `Conversions` — така, както платформата ги е
дала.

## Claude / AI **никога** не променя source data.

AI може да чете суровите данни, да ги обобщава, да предлага изводи и да сочи
аномалии. Не може да ги редактира.

**Причината е практическа, не догматична.** В момента, в който едно число в
суровия слой бъде „поправено“, губиш възможността да провериш каквото и да е
срещу интерфейса на Google Ads. Разминаването става необяснимо, а доверието в
цялата таблица пада.

Ако число изглежда грешно: записва се бележка **в tracker слоя**, суровият
остава непокътнат.

## Полета от Google Ads

Дневно, на кампания:

| Поле | Google Ads API |
|---|---|
| `Date` | `segments.date` |
| `Campaign ID` | `campaign.id` |
| `Campaign Name` | `campaign.name` |
| `Spend` | `metrics.cost_micros` ÷ 1 000 000 |
| `Impressions` | `metrics.impressions` |
| `Clicks` | `metrics.clicks` |
| `Conversions` | `metrics.conversions` |
| `Conversion Value` | `metrics.conversions_value` |

> **`cost_micros` е в милионни части.** 10 000 000 micros = 10 €. Пропуснатото
> деление е класическа грешка, която прави разхода 1 000 000 пъти по-голям.

**`Leads` не идва оттук.** Google Ads брои `generate_lead` конверсии, което е
близко, но не същото като заявка в CRM — може да има дублиране, може да има
заявка при отказано съгласие, която Google не вижда. `Leads` в tracker-а идва
от **CRM**, не от рекламната платформа. `Conversions` се пази отделно, за да
може двете да се сравняват.

## Полета от Meta

| Поле | Meta Marketing API |
|---|---|
| `Date` | `date_start` |
| `Campaign ID` | `campaign_id` |
| `Campaign Name` | `campaign_name` |
| `Spend` | `spend` |
| `Impressions` | `impressions` |
| `Clicks` | `clicks` |
| `Leads` | `actions` където `action_type = lead` |
| `Conversions` | `actions` |

> Meta връща `spend` в основна валута, **не** в милионни части. Двата API-та се
> държат различно — това е първото място, където импортът се чупи.

## Ключ и идемпотентност

## Ключ: `date` + `channel` + `campaign_id`

**`campaign_id`, не `campaign_name`.** Имената се преименуват; ID-тата не.
Импорт по име създава дубликати в деня, в който кампанията бъде преименувана,
и историята се разпада на две.

```
2026-09-14 | google_ads | 21458003912   ← един ред, винаги същият
```

Всеки импорт е **upsert**: ако редът съществува, се обновява; ако не —
добавя се. Пускането на импорта пет пъти дава същия резултат като веднъж.

## Поправки назад

Рекламните платформи **променят данни със задна дата** — филтриране на
невалидни кликове, забавени конверсии, корекции по разхода. Днешното число за
вчера не е задължително същото след три дни.

## Всеки импорт обновява последните **7 дни**, не само вчерашния.

Седем дни покриват типичния прозорец на корекции. Понеже ключът е стабилен,
преизписването е безопасно.

```
Импорт на 14.09  →  обновява 08.09 … 14.09
```

**Следствие:** отчет за месеца не се прави на първо число. Изчаква се поне
седмица, докато последните дни се уталожат.

## График

## Веднъж дневно, след като денят е приключил.

**Препоръка: 04:00 местно време.** Достатъчно късно, за да е затворен вчерашният
ден в двете платформи, и достатъчно рано, за да са налични данните сутринта.

**Не по-често.** Импорт на всеки час дава илюзия за живи данни, но само
пренаписва числа, които и без това ще се променят. Прави отстраняването на
грешки по-трудно и разходва квота.

Не имплементирам фалшив scheduler. Реалните варианти при реализация:

| Вариант | Кога подхожда |
|---|---|
| GitHub Actions cron | Проектът вече е в git; безплатно; без сървър |
| Netlify Scheduled Function | Хостингът вече е Netlify |
| Cloud Run Job / Lambda | Ако автоматизацията порасне |
| Локален Task Scheduler | Само за проба; иска компютърът да е включен |

**За BDS днес: GitHub Actions.** Няма сървър за поддръжка, логовете се пазят,
провалът е видим.

## Формат на суровия слой

Един ред на ден/кампания:

```
date, channel, campaign_id, campaign_name,
spend, impressions, clicks, conversions, conversion_value,
imported_at, source
```

`imported_at` и `source` са одитната следа. Когато число не съвпада с
интерфейса, първият въпрос е „кога и откъде дойде“ — без тези две колони
отговорът липсва.

**Валута:** всичко се записва в **€**. Ако акаунт е в лева, преобразуването
става **при импорта**, с фиксиран курс, записан в бележка. Смесени валути в
една колона правят сумирането безсмислено.

## Обработка на грешки

| Ситуация | Поведение |
|---|---|
| API не отговаря | Повтори 3 пъти с нарастващо изчакване, после спри |
| Частичен отговор | **Не записвай нищо** за този ден — по-добре липса, отколкото половин ден |
| Изчерпана квота | Спри, отбележи, чакай следващия ден |
| Изтекъл token | Спри и **уведоми** — тихо спрян импорт е по-лош от шумна грешка |
| Празен ден (без разход) | Запиши ред с нули — липсващият ред и нулевият ред са различни |

**Последният ред е важен.** Ако кампанията е била на пауза, редът с нули казва
„проверено, нямаше разход“. Липсващият ред казва „не знаем“. При осредняване
разликата е съществена.
